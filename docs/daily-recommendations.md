# Daily local recommendations

Run `pnpm db:migrate` once to add the recommendation snapshot table and a listening-history index. This additive migration does not replace your database or music. Then run `pnpm worker` alongside the web app, using the same `DATABASE_URL` and `.env`.

The worker checks for due accounts on startup and once a minute. It generates a maximum of 50 recommendations per account and saves a snapshot for 24 hours. After downtime it catches up when restarted; it does not promise to run while the machine or worker is off. Up to 100 accounts are scheduled per check, subject to queue capacity. The existing queue supplies leases, heartbeats, cancellation and three retry attempts. A SQLite write transaction and one active refresh pointer per account prevent overlapping web requests and workers from creating duplicate refreshes. A failed refresh retains the previous successful snapshot and its original timestamps; another scheduling attempt is allowed after a one-hour backoff.

`GET /api/intelligence/recommendations` retains `basis`, `tracks`, `totalTracks`, `indexedTracks` and `pendingTracks`. It adds `generatedAt`, `nextRefreshAt` (UTC ISO strings or null), `stale`, `refreshState` (`idle`, `queued`, `running`, `waiting`, `failed`) and `metrics`. A request queues a missing or overdue refresh, then returns the previous snapshot. Until the first job completes, the response includes recently added owned tracks as a clearly labeled cold start, even if the embedding index is empty. A refresh uses cached local EmbeddingGemma vectors and does not call a model, external service, or API requiring a key. Index the library from Discover before expecting semantic personalization.

The ranking uses the latest 10,000 owned play records from the past 30 days. A record qualifies when its reported duration reaches 30 seconds or half the track length, whichever is shorter. Unknown durations, short records, invalid dates, future records and other users' tracks do not contribute. Recency decays exponentially over 14 days; repeated-play weight is capped at three per seed. Up to 25 strong seeds form a similarity profile. Heard seed tracks are excluded and a first ranking pass gives other albums a chance before filling the remaining slots. No favorites, skip rate, completion rate or total listening-time metric is invented. The current player records a scrobble at a playhead threshold: seeking can affect that signal, so `qualifiedPlays` is a count of qualified **recorded plays**, not proof of full listens. `distinctTracks` counts the indexed tracks represented by those qualified records.

The response rechecks track ownership and content against the current library on every read, so deletion, account transfer, or edits cannot expose old private track details from a snapshot. Stored ranking records contain IDs, content hashes and scores; current titles and seed explanations are reconstructed only from owned tracks. Model/revision/dimension changes invalidate an old snapshot and queue a fresh one. While the index is being rebuilt, cold starts remain available.

Saving newly generated embeddings also marks the snapshot due, so indexing can unlock semantic recommendations without waiting for the next daily refresh. Normal listening does not regenerate the list on every page visit; new recorded plays inform the next scheduled refresh.

The worker reads `NUXT_EMBEDDING_MODEL`, `NUXT_EMBEDDING_REVISION`, `NUXT_EMBEDDING_DIMENSIONS` and `NUXT_EMBEDDING_MAX_TRACKS` from the same `.env` as Nuxt. Use the same settings in both processes. The old, unprefixed `EMBEDDING_*` build-time defaults are no longer supported: rename them to `NUXT_EMBEDDING_*` so the built web server and worker select the same model at runtime. Nuxt's production server does not load `.env` automatically; the local launcher explicitly loads it, and deployments must supply these environment variables to both processes. `refreshState: queued` that persists means the worker is stopped or busy. `failed` means its retry budget was exhausted; the one-hour backoff starts at that terminal failure, even after a long queue delay. Consult the local worker logs. User-facing responses do not expose raw job errors or filesystem paths.
